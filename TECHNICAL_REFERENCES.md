# Technical References

While developing *Name Translator*, I used official documentation, open-source examples, and existing libraries to understand how different parts of the system worked. I then adapted these references to fit my own interaction and visual rules.

I did not use these references as finished solutions. They helped me understand basic patterns, which I then changed for the installation.

## 1. Google Gemini API

I used Gemini for handwriting recognition. I referred to the official Gemini documentation and JavaScript image input examples to understand how to send an image from a Node.js server and receive recognised text.

In my project, Gemini only reads the photographed handwriting. The visual character generation happens later in my own JavaScript and p5.js system.

References:

https://ai.google.dev/gemini-api/docs/image-understanding

https://googleapis.github.io/js-genai/

## 2. Google GenAI JavaScript SDK

I used the Google GenAI JavaScript SDK in `recognition.js` to call the Gemini API from the server. I referred to the SDK documentation to understand the basic structure of the request and how image data could be included.

I then connected this API call to my own capture and recognition flow, rather than using the SDK example as a complete project.

Reference:

https://googleapis.github.io/js-genai/

## 3. p5.js

I used p5.js for drawing, animation, and the generated glyphs in the browser. I referred to the p5.js reference when working with canvas drawing, timing, colour, and shape rendering.

For camera input, I referred to the p5.js Video Capture example while learning how browser-based camera input works. It helped me understand the basic relationship between a webcam stream and a canvas drawing loop.

In *Name Translator*, I adapted these ideas for a more specific exhibition workflow. The camera image is cropped to the trace-card area, sent to the server, and then used as the input for handwriting recognition.

References:

https://p5js.org/reference/

https://p5js.org/examples/Imported-Media-Video-Capture/

https://github.com/processing/p5.js

## 4. Socket.IO

I used Socket.IO to send recognition status and results between the browser and the Node.js server.

I referred to the official Socket.IO documentation and repository for the basic client and server event pattern: connecting a socket, emitting an event, and listening for a response. I then changed that structure to fit my own recognition event flow, including `handwriting-submit`, recognition status updates, and the return of the recognised name.

References:

https://socket.io/docs/v4/

https://github.com/socketio/socket.io

## 5. Node.js and Express

I used Node.js and Express to run the local and deployed server, serve the exhibition files, and receive recognition requests.

I followed common Express server patterns to understand how to create routes, serve static files, and start a server. I adapted that structure for the camera capture and recognition process used in this project.

References:

https://nodejs.org/

https://expressjs.com/en/starter/hello-world/

## 6. dotenv

I used dotenv during local development so the Gemini API key could be loaded from a local `.env` file.

The real API key is not included in the GitHub repository.

Reference:

https://www.npmjs.com/package/dotenv

## 7. qrcode

The `qrcode` package remains in the project because it was used in an earlier tablet connection helper.

It is not part of the final character-generation logic.

Reference:

https://www.npmjs.com/package/qrcode

## 8. Render

I used Render to host the submitted web version of the project so it could still be accessed online after the exhibition.

Render provides the `PORT` environment variable automatically, so the deployed server can run without using the fixed local exhibition port.

Reference:

https://render.com/docs/web-services

## 9. Documentation Figures

The documentation figures in `docs/images` use the current project glyph data, colour data, and structural rules through a documentation-only renderer.

This renderer mirrors the current project logic for documentation, but it is not the live exhibition page itself. It is used only to make the README diagrams clearer.

The figures are not generated by an image model.
